# OpenAI 接口 404 错误修复

## 问题描述
使用自动模式时提示 "OpenAI 接口返回状态码: 404"，用户使用第三方 OpenAI 兼容 API（qwen 模型），非 OpenAI 官方 API。

## 根因分析

### 根因 1：不可见零宽字符
模型名 `‌qwen3.6-plus` 前面包含一个**零宽非连接符**（U+200C），是复制粘贴时引入的不可见字符。阿里云 DashScope API 无法识别含隐藏字符的模型名，返回 `model_not_found`（HTTP 404）。

两台机器一台正常一台 404，正是因为其中一台输入模型名时从网页复制了含零宽字符的文本。

### 根因 2：Responses API 误触发（已预防）
`preferResponsesApi()` 在检测到特定模型名时会自动走 `/responses` 端点，第三方兼容 API 不支持该端点。

## 修复内容

### 1. 剥离不可见字符（核心修复）
- **后端** `OpenAiTextClient.safe()` — 增加 `stripInvisibleChars()` 方法，清理零宽字符（U+200B~U+200F, U+202A~U+202E, U+2060~U+206F, U+FEFF 等）
- **后端** `AiConfigServiceImpl.safe()` — 同样增加不可见字符清理，防止脏数据写入数据库
- **前端** `utils.ts` — 新增 `stripInvisibleChars()` 工具函数
- **前端** `connections.ts` — `normalizeModelOptions()` 中对 `openaiBaseUrl`、`openaiModel`、`cliCommand`、`cliWorkingDir` 增加不可见字符清理

### 2. 限制 Responses API 仅在 OpenAI 官方下启用
- `preferResponsesApi()` 增加 `api.openai.com` 域名检测，第三方服务商一律走 `/chat/completions`

### 3. 404 自动降级机制
- `requestText()` 和 `requestTextStream()` 在 Responses API 返回 404 时，自动降级到 Chat Completions API 重试
- 新增 `requestTextWithFallback()` 和 `requestTextStreamWithFallback()` 降级方法

### 4. 增强错误信息
- 所有 HTTP 错误信息中包含：`url`（脱敏）、`model`、`body`（截断），方便排查配置问题
- 新增 `maskUrl()` 方法脱敏 URL
- 新增 `shorten()` 方法截断过长响应体
- 新增 `readErrorBody()` 方法读取流式响应的错误体

### 5. 调试日志
- 在 `requestText()` 和 `requestTextStream()` 入口添加 DEBUG 级别日志，记录实际请求 URL、模型名、API 类型

## 追加：思考模式开关传参支持（2026-05-19）

### 问题
千问等兼容服务商通过 `enable_thinking` 字段控制思考模式，但当前代码中 `thinkingEnabled` 仅控制前端是否展示 thinking 内容，未传递给 LLM API。

### 修复
1. `LlmGatewayRequest` 增加 `thinkingEnabled` 字段
2. `OpenAiTextClient.buildPayload()` 在 Chat Completions 模式下写入 `enable_thinking` 字段
3. `LlmGatewayService.callOpenAi()` 将 `thinkingEnabled` 传递给 `openAiTextClient.requestTextStream()`
4. `AiServiceImpl` 三处构建 `LlmGatewayRequest` 时均设置 `gatewayRequest.setThinkingEnabled(req.getThinkingEnabled())`

## 追加：思考模式展示未根据配置生效（2026-05-19）

### 问题
当 `thinkingEnabled=false` 时，`DisabledThinkingLlmStreamListener` 正确阻止了 `llm.thinking.delta` SSE 事件的推送，但 `thinkingContent` 仍然通过以下路径泄漏到前端：
1. `LlmGatewayService.callOpenAi()` 将 `thinkingContent` 写入 `gatewayResult`
2. `buildTraceLlmCall()` 将 `thinkingContent` 写入 trace
3. `stage.updated` / `trace.snapshot` SSE 事件携带含 `thinkingContent` 的 trace 到前端
4. 前端 `applyStreamTraceSnapshot()` 和 `prepareAssistantMessage()` 从 trace 中提取 `thinkingContent` 并展示

前端 `StudioShell.vue` 仅判断 `item.thinkingContent` 是否非空来展示 Thinking 面板，未考虑 `thinkingEnabled` 配置。

### 修复

#### 后端
- `LlmGatewayService.callOpenAi()` — 当 `thinkingEnabled=false/null` 时，清除 `gatewayResult.thinkingContent`，从源头阻止 thinking 内容泄漏到 trace 和 SSE 事件

#### 前端
- `types.ts` — `QueryChatMessage` 增加 `thinkingEnabled?: boolean` 属性
- `query-chat.ts`:
  - `appendAssistantThinkingMessage()` 接受 `thinkingEnabled` 参数并存入消息
  - `prepareAssistantMessage()` 当 `thinkingEnabled=false` 时清除 `thinkingContent` 和 `thinkingExpanded`
  - `applyStreamTraceSnapshot()` 当 `thinkingEnabled=false` 时不再从 trace 中提取 `thinkingContent`
- `ai-interaction.ts`:
  - 所有 `appendAssistantThinkingMessage()` 调用传入 `ctx.getThinkingEnabled()`（auto 模式传 `false`）
  - 所有 `llm.thinking.delta` 事件处理增加 `thinkingMessage.thinkingEnabled` 前置判断
- `useHistoryModule.ts` — 历史恢复时根据 `thinkingContent` 是否存在推断 `thinkingEnabled`
- `StudioShell.vue`:
  - Thinking 面板展示条件从 `item.thinkingContent` 改为 `item.thinkingEnabled && item.thinkingContent`
  - trace 详情中 Thinking 字段展示条件增加 `item.thinkingEnabled` 判断
